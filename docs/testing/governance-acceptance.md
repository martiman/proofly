# Governance acceptance tests (issue #47)

Project: `backend/tests/Proofly.Acceptance.Tests`. Run: `cd backend && dotnet test tests/Proofly.Acceptance.Tests` (needs PostgreSQL on `localhost:55432`, database `proofly_test`; every test creates and drops its own schema).

## How the tests run

- The real API host (`WebApplicationFactory<Program>`, `Auth:Mode=Local`) with one locally signed token per test user and role (analyst, approver, viewer, configuration administrator, security administrator, plus entity-scoped users).
- The real worker handlers wired as the Worker registers them (`delivery.ingest`, `run.process`, `evidence_pack.generate`), driven one job at a time with `JobProcessor.ProcessOneAsync`. Nothing is simulated: transfers are registered as a delivery, ingested by an in-test CSV adapter (one row is rejected with a reason and never repaired), the other four mandatory sources are inserted as accepted canonical records, and `run.process` evaluates the five controls.
- Neutral GBP/EUR/JPY data built in the tests. The run produces 15 exceptions, two of them blocking (independent ledger `BALANCE_DIFFERENCE` EUR, safeguarding `SHORTFALL` GBP) and one `VALUE_MISMATCH` JPY.
- Test classes run sequentially, each test owns a schema and small connection pools (same conventions as `Proofly.Security.Tests`).
- A refused command is always checked for "no trace": the affected tables and the audit log are snapshotted before and after.

## Defects found and fixed

1. **Resolution commands changed a signed-off run.** `ResolutionCommandRepository.Check` only refused a SUPERSEDED run, so `proposeResolution`, `decideResolution` and `reopenException` succeeded on a SIGNED_OFF run (an open non-blocking exception could be proposed, a resolved blocking one reopened after sign-off). Fix: the same `invalid-state` 409 the other exception commands already return ("The run is signed off and immutable; reprocess the run to change its exceptions"). `src/Proofly.Data/Exceptions/Commands/ResolutionCommandRepository.cs`.
2. **Adjustments on a superseded run answered `invalid-state` instead of `run-superseded`.** The API README says commands against a superseded run fail with 409 `run-superseded`. Fix: new `CommandOutcome.RunSuperseded` for propose and decide, mapped in the endpoint. Signed-off stays `invalid-state`. `AdjustmentCommands.cs`, `AdjustmentCommandEndpoints.cs`.

## Gaps and findings not fixed

1. **Ruleset version of a run.** `RunProcessor` stamps every run with `RunProcessingOptions.RulesetVersion` (the version of the five control implementations) and never consults `IRulesetResolver`, although migration 0045 says `runs.ruleset_version` records the configuration ruleset in force at run start. A run therefore keeps its ruleset trivially (tested), but the next run does not pick up the activated version. Recorded as a skipped test (`ConfigChangeTests.Next_run_after_activation_records_the_activated_ruleset_version`). The resolver itself is tested for the effective-from rule.
2. **Delivery registry ignores the legal entity.** `DeliveryRegistry.RegisterAsync` decides "duplicate", "current delivery" and sequence gaps per source and business date, not per legal entity, so a second entity cannot register its transfer file for the same day (it is rejected with `CORRECTION_LINK_MISSING`). The scope tests therefore insert entity B's records directly and run the real `run.process` handler.
3. **Manual match on a signed-off run answers `run-superseded`** (`ManualMatchOutcome.RunLocked` is mapped to that type for both SUPERSEDED and SIGNED_OFF); every other command says `invalid-state` for signed-off. Status is 409 either way; the test only requires 409.
4. Not covered here: replay of the source commands (`retry-ingestion`, `mark-superseded`), bulk assign and saved views (not governance decisions), and decisions on user-access changes (security administrator), which the security suite covers.
